2 · ADR003 Release candidates
ADR003 · Promote release candidates to PRD
How do we release – so nothing merged is missed, nothing goes back by accident, and we know what is in PRD?


OPTIONS
PROPOSAL
💬 CONCERNS
Before the meeting: add an orange sticky (N), one concern or question per sticky. Put your initials on it.
A. Keep the current process Approve the right runs, re-run what was missed. ✗ Changes still missed  ✗ Old approvals can roll PRD back  
B. Since the last release tag Tag every PRD release; CI builds everything changed since that tag (Score team does this). ✓ Small, proven  ✗ Old approvals can still deploy older images  ✗ Rollback = rebuild  
⭐ C. Release candidates Every merge to main publishes an RC: version of every app + CDK + WSO2. Promote TST → ACC → PRD. ✓ Meets all 5 decision drivers  

Proposal: C. Release candidates
• An RC = the version of every app + CDK stacks + WSO2 config, from one commit of main
• CD compares the RC with the environment and only updates what differs
• A guard refuses an older RC, unless it is a deliberate rollback (ROLLBACK=true)
• Build once: the image tested in ACC is the image in PRD
• Rollback = promote the previous RC (see ADR007)
• Interim if we want the smallest first step: B (its release tag step is reused by C)

📏 Rule that comes with it:
Only merge to main what may go to PRD with the next release.
Unfinished work stays in its PR (show it in the preview environment).
D. Release branches ✗ Branch overhead and merge-back mistakes ✗ Conflicts with trunk-based development and NX affected  
E. Always build and deploy everything ✗ Every release restarts every app ✗ PRD gets images ACC did not test  
F. A pipeline per app ✗ 5 apps × 3 environments = 15 approvals ✗ Portal + BFF and ingestion + CDK need manual coordination

OPTIONS
PROPOSAL
💬 CONCERNS
Before the meeting: add an orange sticky (N), one concern or question per sticky. Put your initials on it.

Release marker
Proposal: M1 + C2 + C3 (C4 pre-fills the notes)
• Annotated tag release/YYYY.MM.DD[.N], placed by the pipeline after a successful PRD deployment
• Tags are never moved or deleted (pipeline has "Create tag" only, no force push)
• Changelog with nx release changelog --dry-run, shown in the CD run before ACC approval, starting from the commit PRD runs (not simply the newest tag – matters after a rollback)
• The PO writes short release notes on the wiki per PRD release (template ready)
• PR titles must follow type(#ticket): description – checked by the PR pipeline
• First tag: release/2026.09.30 on 384f0878 (what PRD runs today)
⭐ M1. Date tag (CalVer) release/2026.10.20 – hotfix release/2026.10.20.1 ✓ Everyone understands "the release of 20 October"  ✓ Easy to automate  
M2. Semantic version (nx release) – v1.4.0 ✗ Needs strict commit discipline + release commit  ✗ "Major" is hard to define for a UI  
M3. Build id only (549747) ✗ Identifies one pipeline run, not a release  
M4. No marker, pipeline history ✗ Invisible in Git, disappears with run retention  
Changelog and release notes
C1. CHANGELOG.md in the repo ✗ Pipeline must push to main (policy bypass) or a release PR  
⭐ C2. Changelog in the pipeline, before approval ✓ Approvers see what they approve  ✓ Pipeline does not write to main  
⭐ C3. Release notes on the wiki, by the PO ✓ Written for people, can link ServiceNow change, tests, stories  
COSTS
PR title check = a new rule for every PR  
Release notes = a new task for the PO every release  
Changelog is not a file in the repo (C1 can be added later)  
⭐ C4. Draft from linked work items (helper for C3) Only as good as PR ↔ work item linking  
C5. A change file per PR (changesets) ✗ Friction for every PR, little gain at our size  
Since 15 April 2026: 78 PRs merged, 60 (77%) follow Conventional Commits. The biggest features do not, e.g. "Feature: Implement Automatic Summary 2.0".

5 · ADR006 Hotfix process
ADR006 · Handle PRD incidents with a hotfix process
When is something a hotfix, and how do we get a fix to PRD fast without skipping safety or losing the fix?


OPTIONS
PROPOSAL
💬 CONCERNS
Before the meeting: add an orange sticky (N), one concern or question per sticky. Put your initials on it.
⭐ H1. Fix forward on main (default) Urgent PR → new RC → promoted quickly ✓ Normal path, no merge back  ✗ Releases everything else on main too  
⭐ H2. Hotfix branch from the release tag (when main is not releasable) hotfix/‹ticket› → RC → ACC → PRD → tag release/‹date›.1 → merge back the same day (Score team does this) ✓ Only the fix goes to PRD  ✗ Needs merge-back discipline  
H3. Cherry-pick into a release branch ✗ We have no release branches (ADR003 option D)  

Proposal: H1 by default · H2 when main is not releasable · H4 for configuration only

Rules
• Last release < 48 h ago caused it and rollback restores service? → Roll back first (ADR007), then fix calmly
• Never skip ACC. At least 1 reviewer who is not the author
• The Engineering Team declares the hotfix and severity; the PO approves PRD
• Post in the team channel at start and end
• Postmortem within 5 working days for Sev 1 and Sev 2
• H2: open the merge-back PR to main at the start; complete it the same day with a normal merge (no squash)
• No PRD release while a hotfix PR to main is still open
⭐ H4. Configuration only Secrets via Key Vault; envVars, CPU, memory via an emergency/ branch in k8s-deployments ✓ Fastest, no build  ✗ Config only, not code  
Severity
🔴 Sev 1 AI Portal down or claims cannot be opened; data of the wrong claim shown; personal data exposed; actively exploitable vulnerability → Hotfix now. Roll back first if the last release caused it.  
🟠 Sev 2 Summary or timeline not loading for many users; event ingestion stopped; critical vulnerability with exposure → Hotfix within the business day  
⚪ Sev 3–4 Cosmetic issues, bugs with a workaround → Normal fix in the next release  
COSTS
CI and CD must accept hotfix/* branches; branch control must allow them  
Branch policy on main must allow a normal merge (no squash) for hotfix/* PRs  
Until CI uses the release tag as NX base, a hotfix must be one commit  
main must stay releasable for H1  
Not in this ADR Support outside office hours → management decision  
✅ Accept
🟡 Accept with action points
❌ Reject

6 · ADR007 Rollback
ADR007 · Roll back by redeploying the previous release candidate
How do we go back to the previous release quickly, safely and visibly?


OPTIONS
PROPOSAL
💬 CONCERNS
Before the meeting: add an orange sticky (N), one concern or question per sticky. Put your initials on it.
R1. Feature flag off ✓ Seconds, one feature only  ✗ We have no flags yet (US 441556) – does not replace rollback  
⭐ R2. Redeploy the previous RC CD run for the previous RC with ROLLBACK=true ✓ Minutes, no rebuild  ✓ Apps + CDK + WSO2  ✓ Visible in history  
⭐ R3. Rebuild from the previous release tag (until RCs exist) Interim ✓ Works today  ✗ Slow: build + 3 environments  ✗ New bits  ✗ Needs quick win N5 (deployProjects)  

Proposal: R2 by default · R3 until RCs exist · never R4 · no manual k8s-deployments changes

⚡ Trigger: Sev 1 within 48 h after a release · 5xx above 2% for 10 min in Splunk · failing health or smoke checks · security exposure
👤 Decision: release captain or The Engineering Team, within 15 minutes; PO informed. Rollback stays a manual decision.
🗄 Retention: keep the last 5 PRD RCs (runs, images, CDK + WSO2 artifacts). RCs that reached ACC get a 30-day retention lease.
🔁 Rehearsal: a rollback drill in ACC every quarter.
R4. ArgoCD rollback button ✗ ArgoCD reapplies Git immediately – does not stick  ✗ No audit trail  
R5. Canary / blue-green (Argo Rollouts) ✓ Automatic  ✗ Not installed on the Cloud Platform Team clusters – future option  
COSTS
Needs release candidates first; until then R3 + quick win N5  
Secrets and values.json (envVars, CPU, memory) are not part of a release – revert them separately  
Artifactory / ECR lifecycle must keep at least 5 PRD versions (to confirm)  
A broken event ingestion version may need an event replay (US 390288)  
Replaced or deleted CDK resources cannot be restored – review the CDK diff in PRs  
✅ Accept
🟡 Accept with action points
❌ Reject
